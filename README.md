# てつづきメトロ / Tetsuzuki Metro

人生の節目に発生する行政手続を「東京の路線図」として可視化し、
**役所への往復回数を減らす**ための Web アプリ。依存ライブラリなし、静的ファイルのみで動く。

**▶ 触ってみる: https://wngbuyx.github.io/tetsuzuki-metro/**

## 1. 何を作っているのか

### 主張

> 遺族や引っ越す人が消耗するのは「手続の数」ではなく **役所への往復回数** である。
> そして最大の原因は、**必要な書類を何通取ればいいか、どの順で回ればいいかを誰も教えてくれない**こと。

一覧表は「何をするか」しか書けない。本作品は**依存関係・条件分岐・期限**を持つグラフとして手続を表現し、
そこから「戸籍謄本は何通いるか」「1回の来庁で何件片づくか」「どの期限は過ぎると取り返しがつかないか」を**計算**する。

### 路線図メタファーの定義

| 路線図の要素 | 意味 |
|---|---|
| 路線 | 分野・管轄（役所線／保険線／年金線／税金線／相続線／民間線／在留線／職場線） |
| 駅 | 個別の手続 |
| 横軸 | 期限までの日数（**対数**）。左に密集し右へ広がる分布そのものが「最初の2週間が地獄」を表す |
| 経路 | ライフイベント（死別・来日・引っ越し・就職・退職・結婚・出産） |
| 乗換 | 同一窓口でまとめて処理できる手続群／複数のライフイベントに現れる手続 |
| 急行通過 | 条件により不要になる手続（マイナンバー登録済みなら年金の死亡届は不要、など） |

## 3. ファイル構成

```

├─ data/
│  ├─ procedures.json          全国共通の手続グラフ（69手続 / 8路線）

│  ├─ documents.json           全国共通の書類（40件）手数料・発行元・取得リードタイム
│  ├─ conditions.json          質問（36条件）シナリオ別・4段階のティア
│  ├─ scenarios.json           ライフイベント定義（7件）＝路線図上の「経路」
│  └─ municipalities/
│     ├─ 131041_shinjuku.json  新宿区：窓口の課・係・電話（36手続分）
│     └─ 131202_nerima.json    練馬区：施設12件（緯度経度・開庁時間つき）
├─ index.html                  Web UI のエントリポイント
├─ css/style.css               全スタイル（Mini Metro 風の作図＋印刷用）
├─ js/
│  ├─ app.js                   画面制御・状態管理（状態は URL ハッシュのみ）
│  ├─ metro.js                 路線図の SVG 描画（オクトリニア作図）
│  └─ i18n.js                  UI ラベルの3言語
├─ src/
│  ├─ route.js                 経路計算エンジン（依存ライブラリ無し・ESM）
│  └─ cli.js                   動作確認用CLI（`npm run route`）
├─ sources/
│  ├─ README.md                一次情報の出所（PDF は再配布可否が未確認のため非同梱）
│  └─ *.py / *.mjs             データ構築・検証に使ったスクリプト（再現用）
├─ package.json
└─ README.md
```

### 三層構造

| 層 | 内容 | 自治体が変わったら |
|---|---|---|
| **全国共通** | 期限・依存関係・必要書類・根拠法令 | 変わらない |
| **自治体別** | 窓口の課名・係名・電話・位置 | `municipalities/` に1ファイル足すだけ |
| **シナリオ** | どの駅を通るか | `scenarios.json` に1件足すだけ |

新しい区への対応も、新しいライフイベントの追加も、この構造なら**1ファイルの追加**で済む。

### 3.5 「死別レジストリ」としての位置づけ — こどもDXとの対応

国（デジタル庁）と東京都は、行政手続を機械可読にする仕組み＝**子育て支援制度レジストリ**
（`t000029d0000000034`、7,812件）を既に持っている。**ただし対象は「子育て」だけ。**
都民の声（c06 生活）は「出産、育児、結婚、**介護・死別**などのライフイベントに伴う手続・支援の案内」を
求めているのに、**死別にはレジストリがまだ存在しない。** 本作品のデータ層はその空白を埋める試作であり、
スキーマは既存レジストリに合流できるよう対応を取ってある:

| 子育て支援制度レジストリ | 本作品 `procedures.json` | 備考 |
|---|---|---|
| `institutionName` | `name` | 本作品は ja / easy / en の3言語 |
| `procedurePeriod` | `deadline` | 本作品は `kind`（irreversible 等の期限種別）と `from`（起算日）を追加 |
| `belongings` | `requires` + `requires_detail` | 本作品は**原本提出/提示のみ**の別を持つ（通数計算の核） |
| `procedureCounter` | `window` | 本作品は自治体ファイルで課・係・電話まで解決 |
| `regulation` | `law` | 根拠法令（未記入分は `EVIDENCE_TODO.md` の作業キューにある） |
| `electronicSubmission` | （今後追加） | |
| `area.areaCode` | `municipalities/` のファイル名（団体コード） | |

本作品にあってレジストリに無いもの＝**手続間の依存関係（`depends_on`）と条件分岐（`appears_when`）**。
「案内の一覧」から「経路の計算」に進むにはこの2つが要る、というのが本作品の主張でもある。

## 4. 動かし方

```bash
npm run route      # デモCLI（7ライフイベント × 想定利用者）
npm test           # エンジンのテスト13件（暦計算・通数の幅・管轄地分離・3値論理）
npm run validate   # データ整合性チェック（参照整合・列挙値・条件式の構文）
npm run audit      # 証拠チェーン監査 → EVIDENCE_TODO.md を再生成
```

依存ライブラリ無し、Node のみで動く。

### エンジンが計算するもの（`src/route.js`）

| 関数 | 内容 |
|---|---|
| `resolveRoute` | 条件から通る駅を決める。**3値論理**（必要／不明／非該当）で、未回答でも駅を消さない |
| `computeDue` / `addCalendar` | **期限を暦で計算する**（3か月≠90日）。起算日は `deadline.from`（死亡日・転居日・知った日…）ごとに解決し、日付が未入力なら「仮置き」フラグを返す |
| `countDocuments` | 書類の必要通数。`submit`（原本提出・返却なし）の数がそのまま通数、`show`（提示のみ）は使い回し。**提出方法が未確認の手続は「要確認」として最少〜最多の幅で返す**（勝手に少なく見積もらない） |
| `groupByWindow` | 同一機関でまとめられる手続群 ＝「1回の来庁で片づく単位」。**引っ越しの旧住所地/新住所地は同じ「市区町村」でも別グループ**（1回にまとめられると嘘をつかない） |
| `timeline` | 期限を対数軸に並べる。`irreversible` を最優先で警告 |
| `detectLeadTimeTraps` | 「7日以内の手続なのに、書類の取得に7日かかる」詰みを事前検出 |

### 出力例（遺族・国保・国民年金・持ち家あり）

```
戸籍謄本  8通 ¥3,600（原本提出8／提示のみ2）
★ 戸籍謄本を8通取る代わりに、法定相続情報一覧図（無料・必要枚数交付）を1回取得すれば、
  8回の提出が1回の取得で済みます。

市区町村  計12件  ← 1回の来庁で12件まとめられる
  ・戸籍住民課 戸籍係  03-5273-3509 → 2件
  ・医療保険年金課 年金係 → 3件  …
```

## 5. 期限の分類（`deadline.kind`）

「何日以内か」より「**どういう種類の期限か**」が重要、というのが設計の核。

| kind | 意味 | 例 |
|---|---|---|
| `irreversible` | **過ぎると選択肢が消える／取り返しがつかない** | 児童手当15日（その月分が永久に消える）、健康保険の任意継続20日（選択肢自体が消滅）、転入届14日（マイナンバーカード失効）、子の在留資格取得30日（**永住者の資格が原則得られなくなる**） |
| `before_action` | 行動の前に済ませる必要がある | 資格外活動許可（働き始める前） |
| `legal` | 法律で決まった期限 | 死亡届7日、住居地届出14日、相続放棄3か月 |
| `claim` | 請求しないともらえない | 葬祭費2年、未支給年金5年、出産育児一時金2年 |
| `window_opens` | **この時期からしか申請できない**（締切ではない） | 在留期間更新（満了日の3か月前から） |
| `practical` | 早めが望ましい | 運転免許証の住所変更 |

死別シナリオは `claim` が8件と多い（**知らないともらい忘れる**）。
来日シナリオは10駅中7駅が critical（**知らないと失効・処罰される**）。痛みの種類が違う。

## 6. 一次情報と、その限界

### 使っているデータ

| 内容 | 出所 |
|---|---|
| 手続の期限・窓口・必要書類 | **新宿区おくやみガイドブック（令和8年4月発行・48ページ）** の「区役所での手続きチェックリスト」を逐条で構造化。`sources/` に同梱 |
| 法定期限 | 各省庁・自治体の公式ページで個別に裏取り（全駅に `source` URL を保持） |
| 窓口の位置・電話 | 東京都オープンデータ「公共施設情報」（自治体標準データセット） |

なお事務局の説明により、**カタログサイトに掲載されていないデータでもオープンデータであれば利用可**と確認済み。

### ★ 実査で判明した3つの事実（発表で使う）

1. **窓口の開庁時間はオープンデータになっていない――区によっては。**
   自治体標準データセットは56列の器を持つが、埋まり方が区ごとに全く違う。
   同じ標準・同じコードで、**練馬区は開庁時間が12/12件入っており、新宿区は0件**。
   千代田区に至っては230施設あるのに**緯度も空**。器はあるのに中身が入っていない。

   | | 新宿区 | 練馬区 | 千代田区 |
   |---|---|---|---|
   | 標準データセット | 56列 | 56列 | 56列 |
   | 緯度経度 | 267/267 | 576/578 | **0/230** |
   | 開庁時間 | **0** | **12/12** | **0** |

2. **「おくやみ」関連のオープンデータは都内に存在しない**（検索ヒットは全て誤マッチ）。

3. **新宿区には既に「おくやみ相談窓口」がある**（03-5273-0819／本庁舎1階／平日9-17・事前予約制）。
   本作品は窓口の否定ではなく**前段の補完**。差別化は「来庁前に・24時間・多言語・依存関係ごと俯瞰」。

### 6.5 ライセンス・出典・免責

| 対象 | 状態 |
|---|---|
| 本作品のコード | MIT（`LICENSE`） |
| 新宿区オープンデータポータルのデータ（公共施設情報など） | **CC BY 2.1 JP** と明記あり → 出典表示のうえ利用 |
| **新宿区おくやみガイドブック（PDF）** | ⚠ ガイドブックの配布ページ自体にはライセンス表記が無い。「公開されているPDF」≠「オープンデータ」。事務局は「カタログ外でもオープンデータであれば利用可」と説明しており、**区の利用規約の確認または区への照会で書面根拠を残すこと**（`HANDOFF.md` の作業項目）。それまで `sources/` の同梱PDFは**再配布しない**（リポジトリを公開する場合は URL 指針に差し替える） |
| 構造化した手続データ（`data/`） | 再配布ライセンスは上記確認後に確定 |

**免責（画面にも出す文言の元）**: 本サービスの期限・必要書類・手数料は各機関の公開情報を
構造化した**目安**であり、法的助言ではない。期限の暦計算は応当日ベースで、**末日が閉庁日の場合の
繰り延べは反映していない**。最新・正確な情報は必ず各窓口で確認すること。
各データの確認日は `verified` フィールドに記録する（未記入分は `EVIDENCE_TODO.md` 参照）。

## 8. 技術メモ（ハマりどころ）

- 東京都オープンデータカタログの CKAN API は、**Git Bash の curl から叩くと日本語クエリが文字化けする**
  （フレーズ検索が0件になり、無関係な結果が返る）。**Python の urllib を使うこと。** User-Agent はブラウザUAが必要
  （Webページは403、APIは通る）。
- 新宿区の標準データセットCSVは **UTF-16**。中央区・豊島区は cp932、世田谷区・杉並区は UTF-8。区ごとにバラバラ。
- BOM 無しファイルに対して `utf-16` デコードは**ほぼ必ず成功してしまう**（中身は文字化け）。
  エンコーディング判定は BOM を見てから、UTF-8 系を先に試す。
